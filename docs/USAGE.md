# 从记录到找回：日常使用

## 资料进来

直接写日记或保存 Markdown 到允许目录即可。日期标题尽量明确，如 `## 2026年10月20日`。补记可分别说明“记录日期”和“事情发生日期”；区分自己与他人、已经发生与将来打算。无需为了 AI 改成表格或失去自然表达。

文章或课程材料要变成知识页时，明确说：

> 把 @这份材料 整理进 Wiki，保留原文的关键例子和没处理的部分。

Agent 确认目标，保存不变来源，检查已有页面，形成来源拆解和必要知识页，更新链接与目录。Raw 是原材料，Wiki 是供以后理解、使用和连接的知识页。普通聊天或上传材料不会自动触发写入。

## 更新进检索库

保存笔记 → 后台检查变化 → 构建并验证新版本 → 成功发布 → 再问新增内容。也可用“检查更新”或 MCP refresh_index。按钮响应不等于更新完成，要看 index_status 的当前状态。失败时旧内容仍可查，新改动可能暂不可查。

## 从库里找回来

> 只查技术资料，解释向量检索，并区分我保存的教程和我真正做过的记录。

> 回顾2026年8月1日到10月31日的日记，保留反复，也告诉我哪些没读到。

> 帮我找关于课程备课的旧笔记，给我能打开的来源。

Agent 应先限定集合，分别核对问题，再读正文；不能只靠第一条结果。核对来源证明引文确实存在，不证明模型每句话都对。重要结论点来源回看。

## 情绪交流

> 我现在只是想说说感受，先别急着给办法。

> 陪我看看最近这段记录，用自然一点的文字，说不准的地方不要替我下结论。

纯倾诉无需强制查库。回顾用已读细节表达，避免把反复解释成持续变好。用户明确要求冷静分析、三条总结或建议时再相应调整。

## 内容出去

查询结果默认只显示在聊天；“把刚才选中的答案保存到 Wiki”才进入写入流程。模型得到的是工具返回的相关片段，不是自动得到整个 Vault。不要把 data、outputs、个人来源或账户配置提交到公开 GitHub。
